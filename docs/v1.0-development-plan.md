## 1. 交付定义

1.0 是同时适配 iPhone 和 iPad 的原生视频分析 App。教练或家长能够在单台设备上完成拍摄 / 导入、慢放、逐帧、画面标注、双视频对比、人体姿态分析、保存与导出分享。

完成条件：TODO 中的 1.0 功能与双端验收通过，有可复现的构建和验证记录，提供 iPhone、iPad 模拟器可安装构建。商店分发与上架按用户要求执行，不将“已经上架”作为本轮开发计划的前置条件。

当前开发分支为 `codex/1.0-development`。拍摄 / 导入、单视频编辑、标注、双视频同步、本机姿态分析与导出已接入完整流程；双端回归见 [1.0 验收记录](v1.0-validation.md)。2026-10-22 用户确认人体识别以辅助估算交付；原 90% 定位目标作为研究参考。V1-048 与最终交付确认已按这一范围完成，当前 Todo 为 62/62。A–C 的早期证据另见 [ABC 验收记录](abc-validation.md)。

## 2. 范围与产品行为

| 能力 | 1.0 实现边界 |
| --- | --- |
| 设备 | Universal App；iPhone、iPad 均有完整功能，分别验收，iPad 使用自适应布局 |
| 数据 | 各设备本机保存；不要求登录、不接入 CloudKit 同步、不提供跨设备互通 |
| 拍摄 / 导入 | 相册、文件导入和 App 内拍摄；高帧率取决于实际设备、镜头与分辨率 |
| 视频分析 | 非破坏性选择片段；1× 至 0.05×、循环、暂停和逐帧操作 |
| 标注 | 直线、箭头、圆 / 椭圆、自由手绘、文字、手动角度；撤销、编辑与时间范围 |
| 双视频 | 同屏布局、各路独立画面调整、人工同步点、联动播放及逐帧 |
| 人体分析 | 录制后本机处理；辅助估算的二维骨架与基础画面角度，明确限制并要求人工复核；支持打击与投球 |
| 动作节点 | 人工标记关键帧；打击、投球提供不同名称，可自行命名 |
| 导出 | 分析截图、单视频慢放、双视频合成；可选择是否包含骨架及角度 |

球棒轨迹、棒头 / 握柄追踪、轨迹校正和球路轨迹均不在 1.0 范围。通用自由手绘仍是标注工具，不包含专用轨迹分析。三维运动学测量、自动动作评分、自动阶段识别、配音制作与云端协作不纳入首版。

人体“关节角度”在首版中指图像平面中的估算值，不将其表述为已经验证的真实三维关节旋转。

## 3. 页面与操作闭环

| 页面 | 主要行为 | iPhone / iPad 要点 |
| --- | --- | --- |
| 素材库 | 创建 / 查找 / 打开分析记录，按运动类型与日期管理 | iPhone 列表；iPad 可使用侧栏与详情 |
| 拍摄 / 导入 | 选择来源、权限处理、帧率设置、录制或导入进度 | 显示设备实际支持能力；拒绝录音仍能拍摄 |
| 单视频分析 | 视频画布、时间轴、逐帧、关键帧、标注、姿态面板 | iPhone 横竖屏可用；iPad 工具区与画布共同适配窗口 |
| 双视频对比 | 设置两路素材、同步点、画面调整和联动操作 | 左右 / 上下布局；活动视频路始终明确 |
| 导出面板 | 选择片段、布局、叠加内容，执行保存或分享 | 预览与导出结果一致；进度可取消 |

主闭环：拍摄 / 导入 → 选择打击或投球 → 选取动作片段 → 慢放与标注 / 姿态分析 → 保存记录 → 导出分享。

对比闭环：选择两段视频 → 分别设定片段与动作同步点 → 调整画面 → 联动查看和标注 → 保存 → 导出合成视频。

打击默认节点名称可包括准备、加载、前脚落地、触球、随挥；投球可包括准备、抬腿、前脚落地、出手、随挥。节点均由用户指定；第一帧和动作同步点不强制绑定。

## 4. 技术方案

### 4.1 工程与模块

最低系统版本 iOS / iPadOS 17，作为工程基线；在 iPhone / iPad 模拟器验证中记录支持条件与限制。Swift + SwiftUI 组织页面，UIKit 承载需要精细触控的视频画布；AVFoundation 负责媒体处理。

已落实的模块边界：

```text
CoachInsights/
  App/                    App 生命周期、依赖装配、导航
  Features/
    Library/ Capture/ Analysis/ Comparison/ Export/
  Core/
    Media/                时间映射、解码、播放、缓存
    Drawing/              标注模型、命中测试、绘制
    Pose/                 PoseEngine、结果、质量与角度
    Storage/              文件与 SwiftData 仓储
    Rendering/            画面变换与导出合成
  SharedUI/
CoachInsightsTests/
CoachInsightsUITests/
research/                 独立研究，不纳入 App target
```

只有原生 App 依赖进入发布目标。Python、研究用 OpenCV、TAPIR 代码和研究权重不参与 1.0 打包。

### 4.2 时间轴和逐帧

- 使用真实样本的 presentation timestamp 和 `CMTime`，不以“秒数 × 名义帧率”代替源帧定位。
- `MediaTimeMap` 处理原始素材、相册慢动作调整、片段范围、播放速度和对比偏移；每种映射都可逆查回原始显示帧。
- 普通连续拖动优先及时预览；松手或逐帧操作进行精确定位。零容差 seek 可能增加解码延迟，需要缓存和请求合并共同解决。[Apple 精确 seek 说明](https://developer.apple.com/documentation/avfoundation/avplayer/seek(to:tolerancebefore:toleranceafter:))
- 保存有边界的邻近帧缓存。高分辨率视频需要降预览分辨率或生成分析代理时，保留原件、源时间映射和逐帧能力；不静默丢失可分析帧。
- 慢放不生成新的运动细节。0.05× 是速度控制，不承诺 AI 补帧；相册中已有慢动作的视频以其导入展示时间线为基准。

### 4.3 统一画面坐标

用同一套 `VideoGeometry` 实现视频像素、规范化坐标、视图坐标与导出画面的转换。统一处理方向、留黑、缩放、平移、裁切和镜像。

标注与姿态结果绑定视频和源时间，持久保存时不依赖屏幕像素。角度计算必须先恢复实际图像比例，不能直接在失真的归一化长宽坐标中计算。预览和导出使用相同模型与绘制规则。

### 4.4 双视频同步

采用一个共享分析时间 `τ`，分别映射到两段视频：`tA = anchorA + τ`、`tB = anchorB + τ`，再各自经过片段及慢动作映射定位真实帧。

两个播放器各自点击播放不能作为同步方案。连续播放使用共享时钟和必要校正；暂停 / 逐帧时按各路真实时间戳选择最近可显示帧。不同帧率的视频不要求相同帧编号。

共同可播放区间由两路片段映射后的交集决定。到达边界时联动停止或按共同区间循环，避免一路停止、另一路继续。1.0 不进行自动动作相位拉伸。

### 4.5 人体姿态引擎

默认实现 `ApplePoseEngine`，通过 `PoseEngine` 接口隔离识别引擎。Vision 提供二维人体关键点及置信分数，坐标原点与屏幕不同，需统一转换。[Apple 人体姿态说明](https://developer.apple.com/documentation/vision/detecting-human-body-poses-in-images)

已在 iPhone 和 iPad 模拟器复现 Vision 缺少模型的运行时缺口，因此接入原生 MediaPipe Full；模拟器直接使用 Full，实际 iOS 代码保留 Vision 优先及错误回退。Heavy 仅作测试对照。原生可用性与人工标注质量分开验收，具体见 [姿态验证记录](pose-engine-validation.md)。增加 SDK 解决了推理可用性，未达到原定精度门槛；不以检出帧数代替定位精度。[MediaPipe 官方 iOS 接入](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker/ios)

仅对选定片段在本机离线分析，不要求在高帧率录制时同步执行 AI。缓存逐帧关键点、置信分数、质量标记、引擎版本和参数，播放时读取结果，避免反复推理。

1.0 指标限定为二维肘角、膝角，以及躯干相对画面垂直方向的倾斜角。必要关键点不可用时显示“不可测”，不以 0° 或推测值填充。模糊、遮挡、多人或主体过小时提示调整拍摄 / 分析区域；不静默跳到其他人物。

不实现身体或球棒的轨迹视图；骨架叠加仅显示当前帧的姿态。

### 4.6 本地数据与恢复

| 模型 | 主要持久字段 |
| --- | --- |
| `VideoAsset` | ID、本机相对路径、尺寸、方向、编码、时长、时间映射版本、内容标识 |
| `AnalysisSession` | 名称、运动类型、日期、素材引用、片段范围、人工关键帧、画面设置 |
| `Annotation` | 类型、视频路、几何坐标、颜色 / 线宽 / 文本、单帧或时间范围、版本 |
| `ComparisonSetup` | 两路素材 / 片段、各自同步点、布局、画面变换、共享播放设置 |
| `PoseResult` | 视频与片段标识、引擎 / 参数版本、逐帧关键点及质量、角度结果 |
| `ExportJob` | 输入快照、导出设置、临时输出、状态、失败与取消信息 |

素材复制进 App 持久目录；元数据使用 SwiftData，显式设置 `cloudKitDatabase: .none`，不添加 iCloud capability。[Apple 关闭 SwiftData 同步说明](https://developer.apple.com/documentation/swiftdata/modelconfiguration/cloudkitdatabase-swift.struct/none)

原视频和用户标注是持久数据；缩略图、解码帧、代理和派生结果按可重建缓存管理。删除记录时检查素材引用，清理孤立文件，不更改相册原件。保存采用安全写入，任务中断可取消 / 重试，不能留下半写入的有效记录。

离线验收使用已完整导入的本机素材。相册或文件提供方尚未准备好的媒体需显示读取 / 获取进度，成功复制后再承诺本机可用。

### 4.7 导出

统一导出模型读取当前分析设置的快照，导出时修改编辑界面不影响正在生成的文件。默认兼容性基线为 1080p、H.264、SDR；HDR 源素材需要明确的色彩转换并进行视觉检查。

截图与单视频可包含标注、骨架和角度；双视频合成为一个文件，保留布局、同步与每路画面设置。原始素材保持不变。

音频基线：原速单视频可播放 / 导出原声，慢放及双视频导出默认静音；界面明确显示设置。首版不制作旁白或混音。

## 6. 验收标准

### 6.1 必须覆盖的素材和设备

- 现有 4K、约 30fps 打击素材保留为本机回归样本，另补充投球素材。
- 覆盖 30 / 60 / 120 / 240fps、可变帧率、相册慢动作、横竖方向与 HDR；仅在设备实际支持的组合中验收拍摄。
- 覆盖不同长短片段、左右手、正面 / 侧面拍摄、遮挡、多人背景与低光；不把一段清晰素材当作普遍精度结论。
- 使用 iPhone、iPad 模拟器；记录型号与系统。分别检查较小 iPhone、常规 iPhone、iPad mini / 常规 iPad 布局及支持的窗口尺寸。
- 使用合成几何与时间轴数据验证数学；实拍素材留在本机，不提交到 Git。

### 6.2 核心功能门禁

| 项目 | 必须达到的行为 |
| --- | --- |
| 逐帧 | 连续前进 N 帧再后退 N 帧回到同一源帧；首尾边界正确；暂停、时间轴和实际画面一致 |
| 慢动作导入 | 展示时间与源帧映射明确；精细分析帧不因导入被静默丢弃 |
| 标注几何 | 旋转、缩放、平移、留黑及布局变化后仍贴合画面，触控位置与落点一致 |
| 标注时间 | 单帧 / 时间范围准确；重新打开后可编辑；撤销 / 重做不破坏其他标注 |
| 双视频 | 同步点正确，精确定位时各路误差不超过该位置的一个源帧间隔；连续播放 / 循环无累计漂移 |
| 人体显示 | 无效关键点不绘制，必要点缺失时角度不可测，分析区域与源时间正确，不跳人物 |
| 保存恢复 | 重新启动后恢复片段、标注、关键帧、对比与姿态设置；源文件不被覆盖 |
| 导出 | 标注位置、时间、骨架、角度、同步、速度和画面方向与预览一致；可在系统播放器打开 |
| 本机使用 | 已导入素材的全部核心流程在离线时可用；无账号、云端推理和自动跨设备同步 |
| 异常处理 | 权限拒绝、低空间、读取失败、取消、中断和低内存均有明确状态，无损坏记录或误删素材 |

### 6.3 人体辅助估算与质量记录

保留至少 60 个关键帧的人工核查集，打击和投球各不少于 30 帧；按人员 / 原片区分调试与验收样本。可明确定位的可见关节作为坐标参考，记录覆盖率、腕 / 肘、左右混淆和高置信错误，不通过排除困难帧掩盖缺失覆盖。

2026-10-22 用户明确确认：1.0 人体识别先作为辅助估算功能，明确识别限制，不再以 90% 作为发布前置。原 PCK@0.05 的 90% 目标保留为后续研究参考，Full / Heavy 的实测值不修改、不表述为已经达到该目标。

当前验收条件：分析、对比、导出和使用说明明确骨架与角度仅为二维辅助估算；遮挡、运动模糊、侧身或多人可能导致点位偏移、左右肢混淆或缺失，高置信度也可能出错，需逐帧人工复核。不承诺三维测量或自动动作评分。无效点不绘制，骨架可关闭，包含可见骨架的预览与导出共用辅助估算标识。离线运行、取消 / 重试、缓存、几何和保存恢复等功能正确性条件继续执行。

### 6.4 性能与可靠性门禁

B 阶段在指定模拟器上记录精确 seek、逐帧、双路播放、姿态探针和采样内存，并锁定可复测的功能与资源阈值；导出在 I 阶段补测。不设置实体设备的相机、能耗或发热验收。模拟器阈值只用于同类环境回归，见 ABC 验收记录。

功能底线：主界面保持可操作；进度可见、操作可取消；缓存有界；内存警告可清理；后台中断可安全取消或重试。预览能力不足时降低预览负担，保留原件与分析精度，不以跳帧掩盖逐帧问题。

### 6.5 必要自动化验证

- 时间映射：可变帧率、慢动作调整、片段裁切、速度和 A/B 同步映射。
- 几何与角度：方向、镜像、留黑、缩放、往返坐标及已知角度的合成数据。
- 持久化：保存重开、引用删除、中断恢复和缓存版本失效。
- 渲染：关键帧标注和导出画面的几何一致性、双路时间关系。
- UI：iPhone / iPad 的导入分析、编辑保存与双视频核心路径；相机能力按系统能力检测与可替换输入进行测试。

不为静态文案或可逆低影响改动堆砌测试；测试重点是媒体精度、数据安全和关键用户流程。

## 7. 风险与处理方式

| 风险 | 处理方式 | 验证位置 |
| --- | --- | --- |
| 逐帧精度与拖动响应冲突 | 预览与精确定位分工、合并请求、邻近帧缓存 | B、E |
| 高帧率 / 双路高分辨率资源不足 | 动态能力检测、受控缓存、分析预览代理、共享时间映射 | B、D、G |
| 视频与叠加坐标不一致 | 统一 `VideoGeometry`，预览 / 导出使用同一模型 | B、F、I |
| 快速投球、遮挡或多人使人体识别失效 | 质量门限、分析区域、分组人工核查、必要时切换引擎 | B、H |
| iPad 旋转或窗口变化破坏操作 | 从工程初期采用自适应布局，每个功能同时验证双端 | A–J |
| 大视频或中断导致数据损坏 | 安全写入、引用检查、任务状态与可重试清理 | C、D、I、J |

## 8. 执行与状态维护

Codex 负责实现、必要测试、双端验证与维护 TODO。每次围绕有依赖闭环的任务推进，记录实现位置、检查结果和未完成条件；独立任务可继续推进，外部条件未满足的任务保持未完成。

分发签名权限或额外拍摄样本需要外部条件时，只提出当前真正缺少的具体资源。不会把这些条件转化为要求用户承担开发工作，所有验收均明确标注模拟器型号、系统和测试结果。

历史球棒追踪研究保留用于查阅，不再进入当前 1.0 的实现路径。后续范围变化同步更新本计划、TODO、README 和产品决策记录。
